# 3D 柜体设计与拆单功能 - 二次审阅修改点

> 审阅日期: 2026-05-19
> 审阅范围: `docs/superpowers/specs/2026-05-19-3d-cabinet-design.md`、`docs/superpowers/specs/修改点.md`
> 说明: 当前仓库未发现 `docs/头脑风暴` 物理目录；本次按现有设计文档目录 `docs/superpowers/specs` 审阅。

## 总体判断

现有设计方向是可行的，旧 `修改点.md` 中关于 3D 位置信息、板件不合并、拆单 execute/confirm 两阶段、外键级联等问题已经被新版设计文档吸收。

但在正式实施前，还建议先调整以下落地点。它们多数不是功能想法问题，而是和当前项目已有代码、数据库字段、租户拦截器、前端排版工作台衔接有关；如果不先定清楚，后续实现容易出现接口能写出来但数据跑不通的情况。

## 1. 新表必须处理 `user_id` 与租户拦截器

**优先级: 高**

当前后端启用了 MyBatis-Plus `TenantLineInnerInterceptor`，`UserIdHandler` 会给非忽略表自动追加 `user_id` 条件。忽略表目前只有:

- `t_user`
- `t_role`
- `t_permission`
- `t_user_role`
- `t_role_permission`

设计文档新增的 `cabinet_template`、`cabinet_order_item` 都不在忽略列表中。如果按当前 SQL 直接建表:

- `cabinet_template` 没有 `user_id` 字段，查询/插入时会被租户拦截器追加 `user_id`，容易直接 SQL 报错。
- `cabinet_order_item` 没有 `user_id` 字段，同样会触发租户字段问题。
- 官方模板 `is_official=1` 如果也走 `user_id = 当前用户`，会出现普通用户看不到官方模板的问题。

建议调整:

1. `cabinet_order_item` 增加 `user_id BIGINT NOT NULL`，并加 `fk_cabinet_order_item_user` 外键与 `(user_id, order_item_id)` 索引，保持和 `t_order_item` 一样的数据隔离方式。
2. `cabinet_template` 不建议简单依赖租户拦截器。更稳的方案是把 `cabinet_template` 加入 `UserIdHandler.IGNORE_TABLES`，然后在 `CabinetTemplateService` 中手动限定:

```sql
WHERE is_official = 1 OR created_by = 当前用户
```

3. 模板编辑、删除必须校验 `created_by = 当前用户` 且 `is_official = 0`；官方模板只能由管理员或初始化脚本维护。

## 2. 字段命名要对齐现有实体主键

**优先级: 高**

设计文档里多处使用了和当前代码不一致的名称:

- `materialId` 指向 `TBoard.id`，但实际实体是 `TBoard.boardId`。
- `cabinet_order_item.order_item_id` 说明关联 `TOrderItem.id`，但实际实体主键是 `TOrderItem.itemId`，数据库列是 `item_id`。
- 设计文档写入 `TOrderItem` 时提到 `l/w`，但实际字段是 `length/width`。

建议调整:

- 柜体 JSON 中把 `materialId` 改成 `boardId`，如果还需要表现“材质”，用 `materialName/color/thickness` 快照字段表达。
- 文档中所有 `TBoard.id` 改成 `TBoard.boardId`，所有 `TOrderItem.id` 改成 `TOrderItem.itemId`。
- `SplitItemVO` 明确映射到现有订单明细字段:
  - `partName`: 板件名称，如左侧板、右门板
  - `partCode`: 工件编号，如 ZG-001
  - `boardId`: 对应 `t_board.board_id`
  - `length/width/thickness`: 实际切割尺寸
  - `quantity`: 第一版固定为 1
  - `materialName/color`: 从 `TBoard` 快照写入
  - `edgeLeft/edgeRight/edgeFront/edgeBack/edgeTop/edgeBottom`: 按统一封边规则转换
  - `isTexture/allowRotation/label/remark`: 按现有 DTO 约定补齐默认值

这样可以减少后端 DTO、前端 API 和数据库脚本之间的翻译层。

## 3. 封边坐标规则仍然不够一致

**优先级: 高**

新版设计文档虽然补充了封边换算规则，但当前示例和规则仍有冲突:

- 规则写 `left/right` 扣 `designWidth`，`top/bottom/front/back` 扣 `designLength`。
- 侧板示例 `edgeBanding: ["front", "top", "bottom"]`，按规则应扣 3mm 长度、0mm 宽度，但输出示例写成 `cutLength=2198`、`cutWidth=598`。
- 门板示例 `edgeBanding: ["left", "right", "top", "bottom"]`，按每条 1mm 规则应分别扣 2mm，但输出示例写成 `2146 × 396`，像是每边扣了 2mm。

建议调整为一套更难误解的模型:

1. 拆单计算使用“板件自身 2D 坐标系”的四条边，不直接使用柜体空间的 `front/back/top/bottom/left/right` 做尺寸扣减。
2. 可以把 `edgeBanding` 改成对象结构:

```json
{
  "edgeBanding": {
    "left": true,
    "right": true,
    "top": true,
    "bottom": false
  },
  "edgeRole": {
    "left": "靠墙侧",
    "right": "前口",
    "top": "上端",
    "bottom": "下端"
  }
}
```

3. 尺寸换算只按板件 2D 边计算:
   - `cutWidth = designWidth - leftEdgeThickness - rightEdgeThickness`
   - `cutLength = designLength - topEdgeThickness - bottomEdgeThickness`
4. 如果确实要保存“前口/后口/顶边/底边”等业务语义，放到 `edgeRole` 或辅助表 JSON 中，不参与尺寸扣减。
5. 文档中的所有封边示例需要重新计算，避免后续代码按错误样例实现。

## 4. `confirm` 不应信任前端传回的拆单明细

**优先级: 高**

当前接口设计中:

```text
POST /order-split/confirm
入参: { orderId: Long, items: [SplitItemVO] }
```

这个设计容易让用户或前端脚本篡改 `cutLength/cutWidth/boardId/hingeHoles` 后直接写入数据库。拆单结果应该由后端按柜体 JSON 重新计算，前端只能确认，不应成为最终计算来源。

建议调整为以下二选一:

1. **无状态方案**: `confirm` 入参为 `{ orderId, cabinetJson }`，后端在事务内重新执行拆单计算并写库。
2. **草稿方案**: `execute` 返回 `splitDraftId`，后端缓存或持久化拆单草稿；`confirm` 入参为 `{ orderId, splitDraftId }`，后端读取草稿并再次校验订单、板材归属和版本。

无论采用哪种方案，`confirm` 都必须在后端校验:

- `orderId` 属于当前用户。
- 所有 `boardId` 属于当前用户且 `is_enabled = 1`。
- 切割尺寸不超过对应 `TBoard.length/width`。
- 写入 `TOrderItem` 和 `cabinet_order_item` 在同一个事务中完成。

## 5. 需要补清“拆单后如何进入排版工作台”

**优先级: 高**

设计文档写了“确认写入订单 → 跳转排版工作台”，但当前前端排版工作台的实际入口有两个:

- `DataInputView` 先在前端组装 `sessionStorage` 草稿，再带 `draftId` 跳转。
- `LayoutWorkbenchView` 通过 `taskId` 加载算法结果，或通过 `draftId` 加载前端草稿。

当前工作台并没有“按 orderId 自动读取订单明细、按板材分组、提交算法并渲染”的完整流程。虽然 `GET /orders/{id}` 会返回 `items`，但工作台现在没有使用它来自动排版。

建议设计文档补一段明确的衔接方案:

1. `confirm` 返回:

```json
{
  "orderId": 123,
  "createdItemIds": [11, 12, 13],
  "nextAction": "layout-workbench"
}
```

2. 前端跳转路径建议为:

```text
/cutting/layout-workbench?orderId=123&source=cabinet
```

3. `LayoutWorkbenchView` 增加按 `orderId` 加载订单详情的逻辑，并把 `order.items` 按 `boardId` 分组生成算法任务。
4. 或者复用现有 `draftId` 机制: 柜体设计页在确认拆单前直接生成和 `DataInputView` 一样的 `layout-draft-*` 数据，先完成排版预览；用户保存排版结果时再绑定订单。

两种路线只能选一条作为第一版主流程，否则会出现拆单写库成功但工作台没有可视化结果的断点。

## 6. 铰链孔建议改成通用孔加工操作

**优先级: 中**

当前 `hingeHoles` 主要描述门板上的铰链杯孔，输出里只有 `positions`。这对“展示提示”够用，但对后续 CNC、标签或质检不够稳定，因为缺少完整的二维坐标和孔所属板件。

建议把拆单输出里的孔信息收敛为通用结构:

```json
{
  "holeOperations": [
    {
      "sourceBoardId": "b-003",
      "workpieceCode": "ZG-003",
      "type": "hinge_cup",
      "face": "inner",
      "x": 22,
      "y": 24,
      "diameter": 35,
      "depth": 12,
      "unit": "mm"
    }
  ]
}
```

如果第一版只计算门板杯孔，不计算侧板安装孔，也应在文档中明确“不输出侧板铰链安装孔，本期仅作为门板开孔提示”。否则“铰链孔位”这个说法容易被理解成完整五金加工数据。

## 7. 模板和拆单快照不要在每条明细里重复存完整柜体 JSON

**优先级: 中**

`cabinet_order_item` 里设计了 `cabinet_json`，说明是“原始柜体 JSON 快照”。如果每个板件都存一份完整柜体 JSON，会带来:

- 数据重复大。
- 一个柜体拆出几十块板时，每行都保存同样的大 JSON。
- 后续排查时难以判断哪一份是完整设计快照的权威版本。

建议二选一:

1. 新增一张更清晰的拆单批次表，如 `cabinet_split_batch`，保存 `order_id/user_id/cabinet_name/cabinet_json/create_time`，`cabinet_order_item` 只保存 `split_batch_id` 和 `source_board_id`。
2. 如果坚持只新增两张表，则把完整柜体 JSON 存到 `t_order.config_json` 或 `cabinet_template.cabinet_json`，`cabinet_order_item` 只保存当前板件的 `source_board_json` 快照。

第一版毕业设计如果想控工作量，方案 2 更轻。

## 8. 数据库迁移说明要匹配当前项目实际方式

**优先级: 中**

设计文档写“Flyway migration”和 `V{next}__create_cabinet_template.sql`，但当前 `pom.xml` 没有 Flyway 依赖，现有脚本命名也采用:

```text
src/main/resources/db/migration/20260509_production_task.sql
```

建议调整:

- 如果不引入 Flyway，就把文档中的“Flyway migration”改成“数据库增量脚本”，命名沿用 `YYYYMMDD_feature.sql`。
- 如果决定正式引入 Flyway，需要同步修改 `pom.xml`、`application.yml`、现有脚本命名与执行说明，这属于“新增依赖”，必须同步更新 `AGENTS.md` 变更记录。

当前更建议先沿用项目已有脚本方式，避免为了一个功能扩大基础设施变更。

## 9. RBAC 与审计日志需要提前定好

**优先级: 中**

新增 `CabinetTemplateController` 和 `OrderSplitController` 后，设计文档只写了“JWT”，没有写权限码与审计行为。当前项目已经有 `@RequirePermission` 和 `@AuditLog`，新增接口应保持一致。

建议第一版复用已有权限，减少 RBAC 迁移:

- 模板列表/详情: `@RequirePermission("order:read")`
- 保存模板、编辑模板、删除模板: `@RequirePermission("order:write")`
- 拆单预览 execute: `@RequirePermission("order:write")`
- 拆单确认 confirm: `@RequirePermission("order:write")` + `@AuditLog(module = "柜体拆单", action = "确认拆单")`

如果要新增 `cabinet:read/cabinet:write` 权限，则需要同步更新 `t_permission` 初始化脚本、角色授权、前端菜单权限和文档接口地图。

## 10. Three.js 依赖应明确使用 npm，不建议 CDN

**优先级: 中**

设计文档写 `Three.js (CDN 或 npm)`。当前前端是 Vite + Vue 3，依赖统一在 `frontend/package.json` 管理，已有 `element-plus`、`pinia`、`vue-router` 等 npm 依赖。

建议改成:

```text
3D 引擎: three npm 包
3D 控制器: three/examples/jsm/controls/OrbitControls.js
```

同时在实施计划中明确:

- `frontend/package.json` 新增 `three`
- 如改用 TypeScript 再考虑 `@types/three`
- 不通过 CDN 引入，避免构建、离线部署和 Docker/Nginx 静态资源路径不一致

## 11. 第一版范围建议收敛成可验收 MVP

**优先级: 中**

当前设计同时包含:

- 预设柜体向导
- 自由拖拽拼装
- 模板保存
- 3D 编辑
- 后端拆单
- 封边换算
- 铰链孔
- 写入订单
- 跳转排版工作台

这已经超过一次小步迭代的范围。建议文档增加分期:

1. **MVP 1**: 只做预设衣柜/地柜参数生成，不做自由拖拽；能预览、拆单、写入订单。
2. **MVP 2**: 接入排版工作台 `orderId` 自动排版链路。
3. **MVP 3**: 用户模板保存/复用。
4. **MVP 4**: 自由拼装、吸附、复杂孔位和更多柜型。

这样更符合项目约定中“小步、明确、可验证”的开发要求。

## 12. 测试清单需要写进设计文档

**优先级: 中**

设计文档目前没有明确测试策略。建议在实施前补充:

- `OrderSplitServiceTest`
  - 单块板正常拆单
  - 封边扣尺寸
  - 扣除后尺寸非法
  - 板材禁用或不存在
  - 板件尺寸超过板材规格
  - 铰链孔均分计算
- `OrderSplitControllerTest`
  - 未登录拒绝
  - 无 `order:write` 权限拒绝
  - execute 不写库
  - confirm 事务写入 `t_order_item` 和 `cabinet_order_item`
- `CabinetTemplateControllerTest`
  - 官方模板可见
  - 用户只能编辑/删除自己的模板
  - 普通用户不能修改官方模板
- 前端构建:
  - `cd frontend && npm run build`

如果引入 Three.js 页面，还应至少用浏览器检查一次 3D canvas 非空、模板生成可见、拆单按钮主流程可走通。
