# 3D 柜体设计与拆单功能 - 第三轮审阅修改点

> 审阅时间: 2026-05-19 19:03
> 审阅对象: `docs/superpowers/specs/2026-05-19-3d-cabinet-design.md`
> 说明: 最新设计文档已经吸收了上一轮关于 `boardId`、封边对象、租户字段、权限、拆单后跳转、测试策略等大部分建议。本文件只记录第三轮新发现或仍需继续收口的点。

## 总体结论

新版设计已经比第一版更接近可实施状态，核心链路“3D 设计 → 后端拆单 → 写入订单 → 排版工作台”基本成型。

但目前还缺几处关键工程约束，主要集中在：目标订单来源、订单明细映射、官方模板中的板材引用、排版工作台自动排样所需的板材规格、算法结果中的工件身份追踪，以及新增接口的权限粒度。建议在正式编码前继续补充这些细节，否则实现时容易出现“拆单能写库，但后续排版、追溯或权限不稳”的问题。

## 1. 3D 设计页缺少目标订单绑定入口

**优先级: 高**

`POST /order-split/confirm` 需要 `orderId`，但 3D 设计页布局和主流程没有说明用户如何得到或选择这个 `orderId`。

当前项目里 `DataInputView` 更多是前端草稿和算法提交流程，并没有稳定地创建 `TOrder` 和 `TOrderItem`；`LayoutWorkbenchView` 保存排版结果时也要求用户先导入一个已存在订单。因此 3D 设计页如果直接确认拆单，会遇到“没有目标订单可写”的断点。

建议补充一种明确入口：

1. 从订单详情页进入：`/cutting/cabinet-design?orderId=123`，只能给已有订单追加柜体拆单。
2. 从 3D 设计页创建订单：页面顶部增加订单信息区，先调用 `/orders` 创建订单，再执行拆单确认。
3. 从加工数据输入页进入：复用已有订单信息草稿，但确认拆单前必须落库生成订单。

第一版建议选择第 1 种，工作量最小，也最符合“可选前置步骤”的定位。

## 2. `confirm` 需要定义追加、替换和重复提交策略

**优先级: 高**

设计文档写 `confirm` 会写入 `TOrderItem + cabinet_order_item`，但没有说明同一个订单重复确认时怎么办。

可能出现的问题：

- 用户连续点击两次确认，重复插入同一批板件。
- 用户修改柜体后再次确认，旧拆单明细是否删除不明确。
- 一个订单包含多个柜体时，是追加第二个柜体，还是替换整个订单明细不明确。

建议补充 `confirmMode`：

```json
{
  "orderId": 123,
  "confirmMode": "append",
  "cabinetJson": {}
}
```

第一版可以只支持：

- `append`：追加一个柜体的拆单明细。

并在响应里返回 `splitBatchCode` 或 `cabinetName`，便于用户知道本次写入的是哪一组柜体。若后续支持重算，则再加入 `replaceCabinet` 或 `replaceAllCabinetItems`。

## 3. `SplitItemVO` 到 `TOrderItem` 的字段映射仍不一致

**优先级: 高**

设计文档现在一处写：

```text
length/width/thickness -> TOrderItem.length/width（thickness 存入辅助表）
```

但当前 `TOrderItem` 和 `TOrderItemDTO` 里 `thickness` 是必填字段，不能只存辅助表。

另外，拆单输出示例中的 `edgeLeft/edgeRight/edgeTop/edgeBottom` 是布尔值，而现有 `TOrderItemDTO` 字段是 `Integer` 且要求 `0/1`。现有订单明细还有 `edgeFront/edgeBack`，设计文档没有说明如何填。

建议明确第一版映射：

| SplitItemVO | TOrderItem | 说明 |
| --- | --- | --- |
| `partCode` | `partCode` | 工件编号 |
| `partName` | `partName` | 板件名称 |
| `boardId` | `boardId` | 原材料板材 |
| `length` | `length` | 切割后长度 |
| `width` | `width` | 切割后宽度 |
| `thickness` | `thickness` | 必须写入订单明细 |
| `quantity` | `quantity` | 第一版固定 1 |
| `edgeLeft/right/top/bottom` | 对应 `edge*` | 布尔值转 `0/1` |
| 无 | `edgeFront/edgeBack` | 第一版固定 0，语义写入辅助表 `edge_role` |
| `grain` | `isTexture` | `vertical/horizontal` 转 1，`none` 转 0 |
| 无 | `allowRotation` | 建议纹理板默认 0，非纹理板按全局参数 |

同时保留 `edge_banding` JSON 到 `cabinet_order_item`，用于追溯原始 2D 封边对象。

## 4. 官方模板不应保存具体 `boardId`

**优先级: 高**

`cabinet_template` 支持官方模板 `is_official=1`，但柜体 JSON 示例中的每个板件都有具体 `boardId`。这对用户自定义模板可以成立，对官方模板不成立。

原因是 `TBoard.boardId` 是用户数据隔离下的板材 ID，不同用户的板材库不一样。官方模板如果保存 `boardId=5/6`，普通用户打开后可能：

- 查不到这个板材。
- 查到的是自己名下另一个完全不同的板材。
- 因租户拦截导致拆单校验失败。

建议区分两类模板结构：

- 官方模板：只保存结构和默认板件类型，`boardId` 为空，使用 `materialSlot` 表示“柜体板/门板/背板”。
- 用户模板：可以保存用户自己的 `boardId`，加载时仍需校验板材是否存在且启用。

示例：

```json
{
  "type": "side",
  "displayName": "左侧板",
  "materialSlot": "cabinet_body",
  "boardId": null
}
```

页面拆单前必须让用户为每个 `materialSlot` 选择实际板材。

## 5. 排版工作台按 `orderId` 自动排版还缺板材规格

**优先级: 高**

设计文档写：

```text
LayoutWorkbenchView 调用 GET /orders/{orderId} 获取 items
将 order.items 按 boardId 分组生成算法任务
```

但当前 `TOrderItemVO` 只有 `boardId`，没有对应 `TBoard.length/width/thickness/brand/materialType/color`。算法任务需要原材料板材的 `L/W`，画布也需要 `_boardGroup` 元数据来显示板材标签。

建议补充一种方案：

1. 后端 `GET /orders/{id}` 返回订单明细时附带 `board` 快照或 `boardLength/boardWidth/boardThickness`。
2. 前端进入工作台后，按 `boardId` 批量调用 `/boards/{id}` 获取板材规格。
3. 新增后端接口如 `GET /orders/{id}/layout-input`，直接返回排版工作台需要的分组结构。

第一版建议选第 3 种，避免前端散落多次查询和转换逻辑。

## 6. 当前算法结果会丢失工件身份

**优先级: 高**

当前算法输入 `Square` 有 `id`，但输出 `PlaceSquare` 只有：

```java
private double x, y, l, w;
```

也就是说排版结果只知道某块矩形的尺寸和位置，不知道它来自哪个 `TOrderItem.itemId`、`partCode` 或 `cabinet_order_item`。如果多个板件尺寸一样，Canvas 上会无法准确追踪“这块是左门板还是右门板”。

这对 3D 拆单尤其重要，因为前面已经决定不合并板件，原因就是要保留位置、封边、孔位等差异。但算法输出如果丢失身份，排版结果追溯会被削弱。

建议在算法输出模型中补充来源 ID：

```java
public class PlaceSquare {
    private String id;
    private double x;
    private double y;
    private double l;
    private double w;
}
```

如果短期不改算法模型，至少在 `LayoutWorkbenchView` 中维护尺寸到待排队列的稳定匹配规则，但这对重复尺寸不可靠。更推荐直接扩展 `PlaceSquare`，并同步更新算法单测、前端画布和小程序算法结果展示。

## 7. 新增控制器不要沿用“读写权限写在类上”的旧模式

**优先级: 高**

当前部分控制器存在这样的写法：

```java
@RequirePermission({"order:read", "order:write"})
```

项目拦截器语义是“拥有任意一个权限即可访问”。如果新增 `OrderSplitController` 或 `CabinetTemplateController` 也把 `order:read` 和 `order:write` 放在类上，那么只有 `order:read` 的用户也可能访问写接口。

设计文档虽然已经给每个接口列了权限，但实施说明还应强调：

- 控制器类上可以只放公共读权限，或不放权限。
- 写接口必须在方法上单独标 `@RequirePermission("order:write")`。
- `confirm` 必须有 `@AuditLog`。

这点建议写进“后端实现约束”，否则开发时很容易复制已有控制器模式。

## 8. 新表时间字段建议对齐项目 `create_time/update_time`

**优先级: 中**

设计文档的新表使用：

- `created_at`
- `updated_at`

但当前项目实体和自动填充器使用：

- Java 字段：`createTime`、`updateTime`
- 数据库字段：`create_time`、`update_time`
- `AutoFillHandler` 只自动填充 `createTime`、`updateTime`

如果新实体使用 `createdAt/updatedAt`，就无法复用现有自动填充规则；如果 SQL 用 `created_at/updated_at`，也会和项目已有表风格不一致。

建议统一改成：

```sql
create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
update_time DATETIME DEFAULT NULL
```

实体字段使用 `createTime/updateTime`，并按需加 `@TableField(fill = FieldFill.INSERT/UPDATE)`。

## 9. 数据库脚本还需要写明执行方式和表选项

**优先级: 中**

设计文档已经从 Flyway 改成了 MySQL 增量脚本，但当前项目没有自动迁移机制。仅写“放入 `src/main/resources/db/migration/`”还不等于会自动执行。

建议补充：

- 脚本需要手动在 `board_cutting_db` 执行。
- 文件开头是否包含 `USE board_cutting_db;`。
- 表使用 `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4`，与已有脚本一致。
- 先建 `cabinet_template`，再建 `cabinet_order_item`。
- 如果加 `cabinet_order_item.user_id` 外键，需确认 `t_user` 已存在且迁移顺序在 RBAC 之后。

这能避免毕业演示或本地部署时“文件放了但库里没有表”的误会。

## 10. `GET /order-items?includeCabinetInfo` 不是无成本扩展

**优先级: 中**

设计文档写：

```text
GET /order-items 可选扩展 includeCabinetInfo 参数
```

当前 `OrderItemController.pageQuery` 只接收 `QueryDTO`，而 `QueryDTO` 只有 `pageNum/pageSize`。如果要支持 `includeCabinetInfo`，需要新增查询 DTO、VO 扩展字段、Service JOIN 或二次查询逻辑。

建议二选一：

1. 暂时删除该扩展点，第一版只在 `GET /orders/{id}` 或新增的 `GET /orders/{id}/layout-input` 中返回柜体拆单信息。
2. 明确新增 `OrderItemQueryDTO extends QueryDTO`，并给 `TOrderItemVO` 增加 `cabinetInfo` 字段。

如果保留该扩展点，还要说明小程序端无需改动，因为默认不传 `includeCabinetInfo`，响应应保持兼容。

## 11. 板材校验要加入厚度和旋转规则

**优先级: 中**

设计文档当前写：

```text
校验长宽尺寸在该板材规格允许范围内
```

这个规则还不完整。当前 `TBoard` 有 `length/width/thickness`，柜体板件 JSON 也有 `thickness`。如果板件厚度和板材厚度不一致，拆单应失败或以 `TBoard.thickness` 为准。

同时，如果允许旋转，尺寸校验不能只判断：

```text
length <= board.length && width <= board.width
```

还要判断旋转后是否能放入：

```text
length <= board.width && width <= board.length
```

建议文档明确：

- 柜体拆单阶段先校验板件厚度必须等于 `TBoard.thickness`。
- 第一版柜体板件如果有纹理方向，默认不允许旋转。
- 排样阶段是否允许旋转由 `allowRotation` 写入订单明细或工作台参数决定。

## 12. 工件编号需要防碰撞规则

**优先级: 中**

设计文档写工件编号格式为：

```text
{柜体简称}{序号}，如 ZG-001、DG-001
```

如果一个订单里有两个“主卧衣柜”，或者用户对同一订单多次追加拆单，`ZG-001` 很容易重复。

建议编号范围至少限定在订单内，并按现有订单明细计算下一号：

```text
{订单号后缀}-{柜体简称}-{三位序号}
```

或：

```text
ZG-001, ZG-002 ... 追加时从该订单现有最大序号继续
```

同时 `cabinet_order_item.workpiece_code` 可以加普通索引，但不建议全局唯一；如要约束唯一，建议用 `(user_id, order_item_id)` 或 `(user_id, order_id, workpiece_code)`，这又需要辅助表保存 `order_id`。

## 13. 设计变更需要同步 AGENTS 和接口地图

**优先级: 中**

该功能会引入：

- 新 API：`/cabinet-templates`、`/order-split/*`
- 新数据表：`cabinet_template`、`cabinet_order_item`
- 新前端依赖：`three`
- 新前端路由：`/cutting/cabinet-design`

按项目约定，实施时不仅要改设计文档，还要同步更新 `AGENTS.md` 的接口地图、数据模型、前端约定和变更记录。设计文档可以提前把这项列入“交付清单”，避免实现完成后忘记项目入口文档。

## 14. 测试策略需要区分 MockMvc 与真实服务写入验证

**优先级: 中**

当前不少模块测试使用 `@MockitoBean` mock service，适合验证控制器路由、参数校验和响应结构。但 `confirm` 的核心风险在事务写入、外键、租户字段和两张表一致性，单纯 mock service 无法覆盖。

建议测试策略补充：

- `OrderSplitControllerTest` 用于验证鉴权、参数校验、响应结构。
- `OrderSplitServiceTest` 验证拆单计算、封边、孔位、编号。
- 至少一个不 mock `OrderSplitService` 的集成测试或手动 SQL 验证，用于确认 `TOrderItem` 与 `cabinet_order_item` 同事务写入。

如果本项目当前测试不连接真实 MySQL，也要在交付说明里写清楚“数据库级外键和级联删除需通过本地 MySQL 手动验证”。
