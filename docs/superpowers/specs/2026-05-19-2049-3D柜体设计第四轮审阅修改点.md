# 3D 柜体设计与拆单功能 - 第四轮审阅修改点

> 审阅时间: 2026-05-19 20:49
> 审阅对象: `docs/superpowers/specs/2026-05-19-3d-cabinet-design.md`
> 说明: 最新设计文档已经吸收第三轮多数建议。本文件只记录第四轮发现的新增断点和仍需进一步明确的实施细节。

## 总体判断

当前设计文档已经进入“基本可开工”的状态，主链路、权限、字段映射、自动排版入口、测试策略和交付清单都比上一版完整。

剩余问题集中在四类：官方模板的 `materialSlot` 如何落到实际 `boardId`、拆单批次如何持久化、从哪个前端页面进入 3D 设计页、以及自动排版时到底排“整单”还是“本次拆单批次”。这些点不补清楚，后续编码时会出现接口参数临时扩展、数据库字段不够用、前端入口找不到的情况。

## 1. `materialSlot` 已提出，但接口入参没有承载板材选择

**优先级: 高**

设计文档说明官方模板中 `boardId = null`，使用 `materialSlot` 表示柜体板、门板、背板，并要求用户拆单前为每个 slot 选择实际板材。

但 `POST /order-split/execute` 和 `POST /order-split/confirm` 的入参仍然只有柜体 JSON：

```json
{
  "orderId": 123,
  "confirmMode": "append",
  "cabinetJson": {}
}
```

这会导致后端无法知道 `cabinet_body`、`door`、`back` 分别映射到哪个 `TBoard.boardId`。如果前端直接把 `boardId` 写回 `cabinetJson`，也需要在文档里明确这是拆单前的标准化步骤。

建议二选一：

1. 在入参中增加 `materialSlotBoardMap`：

```json
{
  "orderId": 123,
  "confirmMode": "append",
  "cabinetJson": {},
  "materialSlotBoardMap": {
    "cabinet_body": 5,
    "door": 6,
    "back": 7
  }
}
```

2. 明确前端在调用接口前必须把所有 `materialSlot` 转换成具体 `boardId`，后端只接受已经解析完成的 `cabinetJson`。

第一版更建议方案 1，因为它保留了官方模板原始结构，也便于后端统一校验 slot 是否漏选。

## 2. `splitBatchCode` 被返回但没有落库字段

**优先级: 高**

设计文档新增了 `splitBatchCode`，用于标识一次拆单写入的完整批次。但 `cabinet_order_item` 表没有 `split_batch_code` 或 `order_id` 字段，只能通过 `order_item_id` 反查 `t_order_item`。

这会带来几个问题：

- 不能按批次查询“本次拆单生成了哪些明细”。
- 无法支持后续按柜体批次删除、重算或展示。
- `LayoutWorkbenchView` 从 `confirm` 跳转后只能拿 `orderId`，不能只排本次新增柜体。
- `splitBatchCode` 返回给前端后没有持久化来源，刷新页面后丢失。

建议给 `cabinet_order_item` 增加：

```sql
order_id BIGINT NOT NULL,
split_batch_code VARCHAR(50) NOT NULL,
source_board_id VARCHAR(50)
```

并增加索引：

```sql
INDEX idx_cabinet_order_batch (user_id, order_id, split_batch_code)
```

`source_board_id` 对应柜体 JSON 中的板件 `id`，用于从订单明细反查到 3D 模型里的原始板件。

## 3. 自动排版需要明确排整单还是排当前拆单批次

**优先级: 高**

文档现在写：

```text
/cutting/layout-workbench?orderId=123&source=cabinet
GET /orders/{orderId}/layout-input
```

如果订单中已经有手工录入的明细或历史柜体拆单明细，工作台会按整单排样；如果用户只想预览本次柜体拆单，就需要按 `splitBatchCode` 过滤。

建议明确第一版行为：

- 如果目标是“整单排样”，跳转只带 `orderId`，`layout-input` 返回该订单全部明细。
- 如果目标是“本次柜体预览”，跳转应带：

```text
/cutting/layout-workbench?orderId=123&source=cabinet&splitBatchCode=ZG-20260519-001
```

并支持：

```text
GET /orders/{id}/layout-input?splitBatchCode=ZG-20260519-001
```

建议第一版选择“整单排样”，因为更符合订单生产流程；但文档应明确，以免前端和后端各按不同理解实现。

## 4. 当前前端没有订单列表/订单详情页，3D 入口不可达

**优先级: 高**

设计文档写第一版从订单详情页进入：

```text
/cutting/cabinet-design?orderId=123
```

但当前前端路由只有：

- 工作台
- 客户管理
- 板材管理
- 用户管理
- 审计日志
- 生产看板
- 加工数据输入
- 排版工作台

并没有独立的订单列表页或订单详情页。因此“从订单详情页进入”在现有前端里没有入口。

建议补清楚第一版入口来源：

1. 在 `DataInputView` 顶栏或底栏增加“3D 柜体设计”按钮，并在进入前先创建或选择订单。
2. 新增 `OrdersView.vue`，提供订单列表和“3D 设计”入口。
3. 在 `ProductionKanbanView` 中对已有订单提供“3D 设计”入口。

如果坚持“订单详情页进入”，那就需要把订单列表/详情页也纳入 MVP 范围，否则 `CabinetDesignView` 会成为只能手动输入 URL 的页面。

## 5. `layout-input` 中的工件 ID 规则要和算法 `Square.id` 对齐

**优先级: 高**

设计文档要求扩展 `PlaceSquare.id`，并说它对应 `TOrderItem.partCode`。但算法输入 `Square.id` 才是放置结果应该原样带回的稳定来源。

如果 `Square.id = partCode`，在以下场景会有冲突：

- 手工订单明细 `partCode` 为空。
- 同一个订单里 `partCode` 重复。
- 某个非拆单订单明细 `quantity > 1`，同一个 `partCode` 对应多块矩形。

建议规定：

```text
Square.id = `${itemId}-${index}`
```

并在 `layout-input` 中返回足够的显示信息：

```json
{
  "itemId": 11,
  "partCode": "ZG-001",
  "partName": "左侧板",
  "length": 2198,
  "width": 600,
  "quantity": 1
}
```

前端构建算法入参时展开为：

```json
{ "id": "11-1", "l": 2198, "w": 600 }
```

排版结果中 `PlaceSquare.id` 回传 `11-1`，前端再用映射表显示 `partCode/partName`。这样能同时兼容 3D 拆单和手工录入订单。

## 6. `PlaceSquare` 增加字段会影响构造器和旧测试

**优先级: 中**

当前 `PlaceSquare` 使用 Lombok：

```java
@AllArgsConstructor
public class PlaceSquare {
    private double x, y, l, w;
}
```

如果直接增加：

```java
private String id;
```

所有 `new PlaceSquare(x, y, l, w)` 的调用都会编译失败，因为全参构造器签名会变成 5 个参数。

建议文档补充实施约束：

- 要么一次性更新所有 `new PlaceSquare(...)` 调用和测试断言。
- 要么保留一个兼容构造器：

```java
public PlaceSquare(double x, double y, double l, double w) {
    this(null, x, y, l, w);
}
```

同时算法放置逻辑必须把 `Square.id` 传入 `PlaceSquare.id`，不是只改 DTO 字段。

## 7. 官方模板示例仍然使用具体 `boardId`

**优先级: 中**

正文已经说明官方模板应使用 `materialSlot`，但 4.1 的柜体结构 JSON 示例仍写：

```json
"boardId": 5
```

这容易让后续实现照着示例把官方模板也写死 `boardId`。

建议把示例拆成两段：

- “拆单请求 JSON”：使用具体 `boardId`
- “官方模板 JSON”：使用 `materialSlot` + `boardId: null`

示例最好至少给一个板件：

```json
{
  "id": "b-001",
  "type": "side",
  "displayName": "左侧板",
  "materialSlot": "cabinet_body",
  "boardId": null
}
```

## 8. `cabinet_template.created_by` 说明有关联用户，但 SQL 没有外键

**优先级: 中**

表字段说明写 `created_by` 关联 `TUser`，但 SQL 中没有外键约束。由于 `cabinet_template` 会被加入租户忽略表，它不受 `user_id` 自动隔离保护，`created_by` 的正确性更重要。

建议补上外键：

```sql
CONSTRAINT fk_cabinet_template_user
    FOREIGN KEY (created_by)
    REFERENCES t_user(user_id)
    ON DELETE SET NULL
```

官方模板 `created_by` 可为空，用户模板必须非空。若不想加外键，也应把字段说明改成“创建人 ID 快照，不建立数据库外键”。

## 9. `cabinet_template` 忽略租户后，需要防止普通用户读取他人模板详情

**优先级: 高**

文档已经写模板列表手动限定：

```sql
WHERE is_official = 1 OR created_by = ?
```

但详情接口 `GET /cabinet-templates/{id}` 也必须应用同样条件。否则普通用户可以枚举 ID 读取其他用户模板。

建议在接口说明中明确：

```text
GET /cabinet-templates/{id}` 仅允许读取 is_official=1 或 created_by=当前用户 的模板。
```

编辑、删除已经有 `created_by = 当前用户 AND is_official = 0`，详情查询也要补上。

## 10. 自动排版权限和菜单权限需要重新核对

**优先级: 中**

当前侧边栏里：

- `layout-workbench` 只需要 `layout:read`
- `data-input` 需要 `order:write`
- 算法接口需要 `algorithm:execute`

设计文档的自动排版流程进入 `LayoutWorkbenchView` 后会自动提交算法。仅有 `layout:read` 的用户可能看得到工作台，却没有 `algorithm:execute` 权限，自动排样会失败。

建议补充权限策略：

- `CabinetDesignView` 菜单或入口需要 `order:write`。
- `source=cabinet` 自动排样时，前端应检查 `algorithm:execute`；无权限时只展示拆单明细或提示无排样权限。
- 如果 `LayoutWorkbenchView` 保持 `layout:read` 可访问，则“手动查看历史排样”和“发起新排样”按钮需要按权限拆开控制。

## 11. `layout-input` 应包含算法参数来源

**优先级: 中**

自动排版时需要的不只是板材组和工件，还包括：

- `gapDistance`
- `allowRotation`
- 是否使用余料
- 锯路/安全边距是否参与算法

当前 `LayoutWorkbenchView` 默认用本地 settings，`DataInputView` 提交算法时写死 `gapDistance: 3`、`isRotateEnable: true`。3D 柜体拆单又建议纹理板件默认不允许旋转。

建议 `layout-input` 至少返回：

```json
{
  "algorithmConfig": {
    "gapDistance": 3,
    "allowRotation": false
  }
}
```

前端仍可允许用户修改，但默认值应来自订单或拆单上下文，而不是隐式使用工作台本地默认。

## 12. 批次回滚或删除策略需要一句边界说明

**优先级: 中**

第一版支持 `append`，但如果用户拆错了柜体，需要知道如何撤销。当前只描述了级联删除 `TOrderItem` 会删除 `cabinet_order_item`，没有给用户侧的批次删除方式。

建议第一版明确：

- 不提供批次级撤销接口，用户可在订单明细中逐条删除，外键自动清理辅助记录。
- 或新增 `DELETE /order-split/batches/{splitBatchCode}`，删除该批次生成的订单明细。

如果前面采纳 `split_batch_code` 落库，未来做批次撤销会自然很多；即使第一版不做，也建议在文档中写明“不在本期范围”。

## 13. 设计文档状态建议改成“待补充实施细节”

**优先级: 低**

文档头部仍写：

```text
状态: 设计完成，待实施
```

但目前仍有接口入参、批次表字段、前端入口、权限拆分等关键细节待定。建议改成：

```text
状态: 设计基本完成，待补充实施细节
```

等 `materialSlotBoardMap`、`splitBatchCode` 落库和前端入口确定后，再改回“设计完成”。
