# 3D 柜体设计与拆单功能 - 收口审阅修改点

> 审阅时间: 2026-05-19 20:59
> 审阅对象: `docs/superpowers/specs/2026-05-19-3d-cabinet-design.md`
> 说明: 这是收口审阅。本轮不再展开大范围方案讨论，只记录仍会阻塞实施、导致 SQL 失败、接口契约不一致或前端入口断裂的问题。

## 总体结论

这份设计文档已经可以进入实现准备阶段，不需要继续无限审。剩余问题不是方向性问题，而是几处需要在开工前修平的工程细节。

建议处理完本文档中的高优先级项后，就停止设计审阅，进入 MVP 1 实现。后续问题通过实现任务和测试反馈收敛，比继续纸面审阅更有效。

## 1. 数据库脚本中 `cabinet_template` SQL 当前会直接执行失败

**优先级: 高**

当前脚本片段存在重复索引和缺少逗号的问题：

```sql
INDEX idx_category (category),
INDEX idx_is_official (is_official)
INDEX idx_category (category),
INDEX idx_is_official (is_official),
```

第二行末尾缺逗号，同时 `idx_category`、`idx_is_official` 被重复定义。MySQL 执行会失败。

建议改成：

```sql
INDEX idx_category (category),
INDEX idx_is_official (is_official),
CONSTRAINT fk_cabinet_template_user
    FOREIGN KEY (created_by)
    REFERENCES t_user(user_id)
    ON DELETE SET NULL
```

这是开工前必须修的硬错误。

## 2. `cabinet_order_item.order_id` 缺少外键约束

**优先级: 高**

文档表字段写：

```text
order_id BIGINT NOT NULL | 冗余 t_order.id
```

当前项目实际订单主键是 `t_order.order_id`，不是 `t_order.id`。另外 SQL 里新增了 `order_id` 字段，但没有对 `t_order(order_id)` 建外键。

建议修正为：

```sql
order_id BIGINT NOT NULL,
INDEX idx_cabinet_order_order (user_id, order_id),
CONSTRAINT fk_cabinet_order_item_order
    FOREIGN KEY (order_id)
    REFERENCES t_order(order_id)
    ON DELETE CASCADE
```

字段说明也应改成“冗余 `t_order.order_id`，便于按订单查询拆单批次”。

## 3. `execute` 接口也需要 `materialSlotBoardMap`

**优先级: 高**

文档已给 `confirm` 增加：

```json
"materialSlotBoardMap": {
  "cabinet_body": 5,
  "door": 6,
  "back": 7
}
```

但 `POST /order-split/execute` 仍写“入参：柜体结构 JSON”。如果用户从官方模板进入，模板里的板件 `boardId = null`，`execute` 预览拆单同样需要知道每个 `materialSlot` 对应哪个板材。

建议把两个接口统一成请求 DTO：

```json
{
  "cabinetJson": {},
  "materialSlotBoardMap": {
    "cabinet_body": 5,
    "door": 6,
    "back": 7
  }
}
```

`confirm` 在此基础上额外包含 `orderId` 和 `confirmMode`。这样 preview 和 confirm 用同一套板材解析与校验逻辑。

## 4. `DataInputView` 当前没有真正的订单创建/选择流程

**优先级: 高**

最新版设计写第一版从 `DataInputView` 进入，并“选择或创建订单”。但当前 `DataInputView.vue` 只是维护前端本地订单信息草稿，提交时直接调用算法，并没有调用 `/orders` 创建订单，也没有订单选择 UI。

而后端创建订单 `TOrderDTO` 至少需要：

- `customerId`
- `processName`

当前 `DataInputView` 里的 `customer` 是文本，不是 `customerId`；也没有明确 `processName` 来源。

建议在 MVP 1 中明确补一项前置任务：

```text
DataInputView 增加订单选择/创建能力，3D 柜体设计入口只在已有 orderId 后可用。
```

或者先新增一个极简订单选择弹窗，调用 `/orders?pageNum=1&pageSize=...` 选择已有订单。否则 `/cutting/cabinet-design?orderId=123` 的入口仍然不可达。

## 5. 参数校验测试不应写成 HTTP 400

**优先级: 高**

测试策略里写：

```text
confirm 入参缺少 orderId 或 cabinetJson → 400
```

但当前项目 `GlobalExceptionHandler` 对参数校验统一返回 `Result.error(...)`，HTTP 状态仍是 200。现有控制器测试也大量断言：

```java
status().isOk()
jsonPath("$.code").value(0)
```

除非本功能要顺带改变全局错误响应契约，否则测试策略应改为：

```text
confirm 入参缺少 orderId 或 cabinetJson → HTTP 200，Result.code=0，data 中包含字段错误
```

这属于项目接口契约一致性问题，建议按现有模式走。

## 6. `layout-input` 返回结构与现有画布元数据还需对齐

**优先级: 中**

`layout-input` 当前返回：

```json
{
  "boardId": 5,
  "boardLength": 2440,
  "boardWidth": 1220,
  "boardThickness": 18,
  "boardName": "18mm暖白柜体板"
}
```

但现有前端画布和板材分组逻辑更习惯使用 `board` 对象，并从中读取：

- `board.boardId`
- `board.length`
- `board.width`
- `board.thickness`
- `board.brand`
- `board.materialType`
- `board.color`
- `board.sizeType`

如果只返回 `boardName`，前端需要额外转换。可以转，但文档要明确。

建议把 `layout-input` 改成更贴近现有结构：

```json
{
  "board": {
    "boardId": 5,
    "length": 2440,
    "width": 1220,
    "thickness": 18,
    "brand": "兔宝宝",
    "materialType": "柜体板",
    "color": "暖白",
    "sizeType": "标准板"
  },
  "items": []
}
```

这样可减少 `LayoutWorkbenchView` 的适配代码。

## 7. `PlaceSquare` 示例代码不应同时依赖 Lombok 全参构造和手写全参构造

**优先级: 中**

文档示例里写了手写构造器，同时在构造器上标了 `@AllArgsConstructor`：

```java
@AllArgsConstructor
public PlaceSquare(String id, double x, double y, double l, double w) { ... }
```

`@AllArgsConstructor` 是类级 Lombok 注解，不应该标在构造器上。建议文档示例改成普通 Java：

```java
@Data
@NoArgsConstructor
public class PlaceSquare {
    private String id;
    private double x, y, l, w;

    public PlaceSquare(double x, double y, double l, double w) {
        this(null, x, y, l, w);
    }

    public PlaceSquare(String id, double x, double y, double l, double w) {
        this.id = id;
        this.x = x;
        this.y = y;
        this.l = l;
        this.w = w;
    }
}
```

或者保留类级 `@AllArgsConstructor`，只手写 4 参数兼容构造器，不要把注解写在构造器上。

## 8. `cabinet_template.created_by` 的“官方模板为空”与用户模板必填应写进校验

**优先级: 中**

SQL 允许 `created_by` 为空，适合官方模板。但用户保存模板时，如果不强制写入当前用户 ID，后续 `created_by = 当前用户` 的查询和编辑校验都会失效。

建议补充服务层规则：

- `POST /cabinet-templates`：强制 `created_by = UserContext.currentUserId`，`is_official = 0`
- 官方模板仅通过初始化 SQL 插入，普通用户接口不能创建 `is_official = 1`
- `created_by` 为空的模板只能是官方模板

这能防止租户忽略表中的用户模板变成“无人拥有”的孤儿数据。

## 9. 收口建议：处理完上述 5 个高优先级项即可进入实现

**优先级: 低**

不建议继续无限追加设计审阅。建议把后续流程定成：

1. 修正设计文档中的 SQL 和接口 DTO。
2. 开始 MVP 1 后端实体、表脚本、拆单服务和 MockMvc 测试。
3. 后端通过后再接 `CabinetDesignView`。
4. 最后再做自动排版工作台衔接。

这时问题会从“假设风险”变成“测试失败或页面走不通”，反馈会更具体，也更省时间。
