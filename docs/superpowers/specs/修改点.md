## 1. 柜体 JSON 缺少 3D 位置信息

现在 `boards` 里有板件类型、尺寸、厚度、纹理、封边、铰链孔，但没有：

- `position`: x / y / z
- `rotation`: x / y / z
- `normal` 或放置方向
- `parentCabinetId`
- 板件之间的连接关系

也就是说，后端可以拆尺寸，但**无法根据 JSON 还原这个柜体在 3D 空间中的真实结构**。如果只是拆单还勉强够用，但如果要保存模板、重新打开设计、继续编辑，就不够了。

建议把板件 JSON 改成类似：

```
{
  "id": "b-001",
  "type": "side",
  "displayName": "左侧板",
  "materialId": 5,
  "designLength": 2200,
  "designWidth": 600,
  "thickness": 18,
  "position": { "x": -591, "y": 1100, "z": 0 },
  "rotation": { "x": 0, "y": 0, "z": 0 },
  "grain": "vertical",
  "edgeBanding": ["left", "right", "top"],
  "hingeHoles": []
}
```

## 2. “同一规格板件自动合并数量”和辅助表设计有冲突

文档里写了“同一规格板件自动合并数量”，拆单输出里也有 `quantity` 字段；但 `cabinet_order_item` 又设计成 `order_item_id BIGINT UNIQUE`，也就是一个订单明细只能对应一条辅助记录。

问题是：如果两个板件尺寸一样，但位置、用途、封边、孔位、工件编号不同，合并后会丢信息。

例如：

- 左侧板、右侧板尺寸一样，但封边方向可能不同；
- 两块门板尺寸一样，但铰链孔方向不同；
- 同规格层板数量为 3，但你仍然可能需要追溯每一块来自哪个柜体位置。

建议第一版先**不要自动合并**，每个板件生成一条 `TOrderItem`，最稳。后面如果要合并，可以增加一个 `source_board_json` 字段保存原始板件列表。

比如：

```
source_boards JSON COMMENT '合并前的原始板件列表'
```

或者在文档里明确：只有在“尺寸、材质、封边、孔位、纹理方向、板件类型完全一致”时才允许合并。

## 3. 封边扣尺寸规则需要写得更精确

现在写的是“每条封边扣除 1mm”，例子是 600×400，左/右/顶封边后变成 598×399。这个例子能看懂，但规则还需要明确：

- `left/right` 是扣 `designWidth`
- `top/bottom` 是扣 `designLength`
- 每条封边扣除量默认 1mm
- 扣完后的尺寸不得小于 0
- 是否按封边厚度字段计算，还是固定 1mm

建议补一段：

```
封边换算规则：
left/right 作用于宽度方向，每存在一条封边，cutWidth 减 1mm；
top/bottom 作用于长度方向，每存在一条封边，cutLength 减 1mm。
例如设计尺寸 600×400，left/right/top 三条封边，则 cutWidth = 600 - 2，cutLength = 400 - 1。
```

这样开发时不会把长宽方向弄反。

## 4. 铰链孔位规则还不够落地

目前文档里写了 `even` 模式，首孔距边 100mm、末孔距边 100mm，并输出坐标偏移。

但还缺几个关键字段：

- 孔径，比如 35mm 铰链杯孔；
- 孔深；
- 距门边距离，比如 21mm 或 22mm；
- 沿哪个方向排布，是沿高度方向还是宽度方向；
- 左开门、右开门如何区分；
- 门板铰链孔和侧板铰链安装孔是否都要算。

另外，示例里 `count: 3`，positions 写的是 `[100, 500, 900]`，如果是 2200 高度并且首末孔距 100mm，均分结果更像 `[100, 1100, 2100]`。建议把示例改严谨，不然 Claude 或开发工具会照着错误例子生成代码。

## 5. “拆单服务只计算，不直接写库”这句话需要调整

文档一处写“拆单服务只计算，不直接写库”，但接口里又有 `/order-split/confirm`，用于确认拆单并写入 `TOrderItem + cabinet_order_item`。

这个不是大问题，但表达上容易矛盾。建议改成：

```
拆单服务分为两个阶段：
1. execute：只做拆单预览计算，不写库；
2. confirm：在用户确认后，以事务方式写入 TOrderItem 和 cabinet_order_item。
```

这样更清楚，也方便后面做事务控制。

## 6. 数据库迁移脚本缺少外键和级联删除

文档里写“删除 `TOrderItem` 时级联删除对应 `cabinet_order_item`”，但 SQL 里没有写外键约束。

如果要真的级联删除，需要补：

```
CONSTRAINT fk_cabinet_order_item_order_item
FOREIGN KEY (order_item_id)
REFERENCES TOrderItem(id)
ON DELETE CASCADE
```

如果你的毕业项目里不想加外键，也要把文档改成：

```
删除 TOrderItem 时，由业务代码同步删除 cabinet_order_item。
```

两种只能选一种，不然文档和数据库实际行为不一致。

## 7. “板件库管理员可扩展”但没有对应数据表

需求决策里写了“板件库：系统预置 + 管理员可扩展”，但是数据表只加了 `cabinet_template` 和 `cabinet_order_item`，没有板件类型配置表。

如果你只是做毕业设计，建议先改成：

```
板件库：系统内置固定类型，包括侧板、层板、门板、背板、顶板、底板，本期不做管理员扩展。
```

这样工作量小很多。

如果真的要管理员扩展，那就需要加一张类似：

```
cabinet_part_type
```

字段包括：类型编码、类型名称、默认厚度、默认封边规则、是否启用、排序号等。
