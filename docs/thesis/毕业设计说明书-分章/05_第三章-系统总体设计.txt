3 系统分析与设计
3.1 系统需求分析
　　系统主要面向中小型柜门板材加工场景，用户需要完成客户信息维护、板材规格维护、待切尺寸输入、排样计算和结果查看等操作。
　　系统功能需求包括：用户登录与身份校验、客户信息新增与查询、板材信息新增与管理、排样参数输入、排样算法求解、排样结果表格展示和排样图形化展示。
　　系统非功能需求包括：接口响应稳定、输入参数具备基本校验、操作流程清晰、移动端页面便于使用、算法结果能够直观展示，并具备后续扩展能力。
3.1.1 可行性分析
　　技术可行性方面，本系统采用 Spring Boot、Vue 3 和 MySQL 作为主要技术栈。Spring Boot 负责后端接口与业务逻辑处理，Vue 3 负责前端页面和交互，MySQL 负责业务数据持久化。排样算法部分采用 Java 自主实现，主要由禁忌搜索和天际线放置算法组成，不依赖额外的商业优化库。因此，从项目开发、环境部署和毕业设计实现难度来看，该技术方案具有可行性。
　　经济可行性方面，系统开发所需的软件环境和工具基本为开源或免费产品，例如 JDK、Spring Boot、MySQL、Vue、Vite 和 ApiFox 等。系统运行阶段不需要购买专门的客户端软件，用户通过浏览器即可访问。对于柜门板材加工业务而言，系统如果能够减少重复录入、降低人工排版时间，并提高部分订单中的板材利用率，就可以在一定程度上减少材料浪费和人工核对成本。
　　操作可行性方面，系统前端采用后台管理系统中常见的表格、表单、按钮和弹窗交互方式，用户学习成本较低。加工数据输入页面按照板件尺寸录入习惯组织字段，用户可以逐行填写板件名称、长度、宽度、数量和旋转设置。排版工作台使用 Canvas 显示板材轮廓和板件位置，相比只显示坐标数据，更便于加工人员理解排样结果。因此，系统在操作流程上能够适配柜门板材切割排版的基本使用场景。

　　生产任务管理用于根据已确认的排版结果生成生产加工任务。当订单完成排版并确认排版方案后，系统可以根据排版结果生成对应的生产任务。生产操作员可以查看任务详情，并根据实际加工进度变更任务状态，如待加工、加工中、已完成或已取消等。

　　余料管理用于管理切割过程中产生的可再次利用板材。系统在排版计算完成后记录余料信息，生产操作员可以查看余料列表，按照材质、尺寸等条件查询可用余料，并对余料状态进行标记。余料状态主要包括可用、已使用和已报废。通过余料管理功能，可以提高余料复用率，进一步提升板材利用率。
3.1.3 功能需求
　　系统面向系统管理员、组织管理员、操作员和生产员四类角色用户，划分为六个功能模块。
　　（1）用户认证与基础数据管理。用户注册、登录、登出，基于JWT的无状态认证，受保护接口须携带Token。客户信息与板材规格的增删改查、分页查询及批量启用/禁用/删除。用户账号管理与启用控制。
　　（2）订单管理。订单的增删改查与状态流转（待处理→生产中→已完成/已取消），每个订单下挂多个待切割板件明细。订单明细包含产品名称、数量、长宽尺寸、材质、封边要求等字段。
　　（3）切割排版（核心模块）。加工数据输入页：选择订单与板材规格后，在可编辑表格中输入待切割板件数据，支持键盘导航和TSV粘贴；底部实时汇总板件统计信息；确认后一键提交排版计算。排版工作台：左侧展示历史排版记录列表，中央Canvas画布以二维图形渲染排版方案（支持缩放、平移、工件悬停tooltip、多容器标签切换）；工具栏提供参数配置（旋转开关、切割间隙、容器尺寸）、排版触发、结果导出等功能。排版算法引擎：接收容器尺寸与矩形列表，通过禁忌搜索优化排列顺序、天际线算法确定放置坐标；支持旋转与间隙参数；当单容器无法容纳全部板件时自动启用多容器迭代拆分；支持异步提交与多策略对比。
　　（4）余料管理与生产看板。排版完成后自动记录余料信息（尺寸、材质、来源），供后续排版优先复用。从订单创建生产任务，以看板分栏视图展示任务状态与进度，支持状态流转。
（5）权限与组织管理。系统采用基于角色的访问控制（RBAC），定义系统管理员、组织管理员、操作员和生产员四种角色，通过权限编码对各功能模块的读写权限进行细粒度控制。系统支持多组织数据隔离，不同组织的业务数据相互独立，组织管理员可在本组织内管理成员账号。系统还提供操作审计日志功能，对关键业务操作进行自动记录，便于事后追溯。
（6）三维柜体设计。系统基于Three.js构建交互式三维柜体设计工作台，支持参数化创建柜体、模板管理、板材拖放装配、吸附对齐、材质渲染、属性编辑和撤销重做等功能。设计完成后可通过拆单流程将柜体分解为待切割板件，并自动路由至排版工作台进行排样计算。
3.1.4 非功能需求
　　性能：常规接口响应≤500ms，50件以内排版计算≤30s。
　　安全性：JWT鉴权覆盖所有业务接口，密码BCrypt哈希存储，参数化查询防注入。
　　一致性：接口统一返回{code, msg, data}结构，前端统一处理和展示错误。
　　可维护性：后端Controller-Service-Mapper分层、前端按模块拆分API客户端与组合式函数、数据库变更通过增量迁移脚本管理。算法模块自包含，各子模块（禁忌搜索、天际线放置、禁忌映射树）相互解耦，便于独立调参与测试。
3.2 系统总体设计
根据前文的需求分析部分，柜门板材切割排版系统需要同时完成基础的业务数据管理、权限与组织管理、订单加工数据录入、排样算法计算、结果可视化展示、生产任务管理，以及三维柜体设计等功能。为了使系统结构更加清楚一点，也为了方便今后功能的扩展，本文采用B/S架构和前后端分离的开发模式，并且将前端按角色分成了Web端和小程序端两个部分。系统整体上被划分为用户层、前端表现层、后端服务层、排样算法层和数据存储层。系统管理员、组织管理员和操作员通过浏览器访问Web前端，生产员则通过小程序访问前端；前端主要负责页面展示、表单输入、排样结果可视化和用户交互等工作；后端主要负责身份认证、权限控制、业务逻辑处理、数据访问以及算法调用；数据库用于保存用户、角色、权限、组织、客户、板材、订单、订单明细、排样结果、余料、生产任务、柜体模板和审计日志等这些业务数据。
在系统的运行过程当中，系统管理员、组织管理员、操作员和生产员这四类角色的用户通过登录页面完成身份认证的过程。登录成功以后，后端会根据用户的角色返回对应的权限编码的集合，前端据此进行路由的分发和菜单的过滤：系统管理员进入系统概览页面，组织管理员和操作员进入工作台，生产员在小程序端进入“我的任务”页面。生产员可以查看操作员分发过来的订单任务，每一个订单任务都会被分发到自己的任务通知里面，并且支持查看任务的明细，另外还设有一个个人设置页面。系统管理员可以管理组织和全局的账号；组织管理员可以维护本组织的客户信息和板材信息，也可以管理组织的成员；操作员可以创建加工订单并且录入需要被切割的板件尺寸，还可以通过三维柜体设计工作台进行柜体的设计并拆单，从而生成板件数据。
当用户在加工数据输入页面设置好了排样参数之后，前端会通过Axios向后端发送排样请求，并且在请求头当中携带JWT令牌。后端接收到请求以后，首先通过TokenInterceptor来校验用户的身份和操作的权限，然后再对参数进行校验并完成业务数据的转换，最后再去调用排样算法模块进行计算。排样算法模块主要是通过禁忌搜索算法来优化板件的排列顺序，同时结合天际线放置算法计算板件在原料板中的具体放置坐标。如果一张板材不能放下全部的板件，系统会继续采用多容器迭代的方式，对剩下的板件继续进行排样。最后，后端将板材利用率、使用板材数量、板件坐标以及旋转状态等这些结果返回给前端。前端再通过表格和Canvas图形化的方式对排样结果进行展示，并且把排样结果保存到数据库当中，这样可以为后续的余料管理和生产任务管理提供一定的数据支持
　　系统总体设计如图3-4示。
　　
图 34系统总体设计图
　　由图3-4可以看出，系统各层之间的职责比较明确。前端表现层主要面向用户的实际操作，提供登录、客户管理、板材管理、订单管理、加工数据输入、排版工作台、生产看板、三维柜体设计、权限与组织管理以及审计日志查看等功能。后端服务层主要通过Spring Boot实现业务接口，并对用户认证、权限控制、客户管理、板材管理、订单管理、排样结果管理、余料管理、生产任务管理、柜体模板管理和审计日志等模块进行统一处理。排样算法层是系统中比较重要的部分，主要负责把业务输入数据转换为算法可以处理的数据，并输出可以用于前端绘图和结果保存的排样坐标数据。数据存储层则通过MySQL对系统中的核心业务数据进行持久化保存和管理。
　　在权限控制方面，系统在后端服务层引入了基于角色的访问控制机制。TokenInterceptor在请求到达Controller之前，从JWT token中提取用户角色信息，并通过数据库查询获取对应的权限编码集合。Controller方法上的@RequirePermission注解声明了该接口所需的权限码，拦截器在执行业务逻辑前进行校验，从而实现接口级别的权限控制。在数据隔离方面，系统通过MyBatis-Plus的TenantLineInnerInterceptor实现多组织数据隔离。该拦截器在SQL执行前自动为查询语句添加组织ID过滤条件，使客户、板材、订单、排样结果和生产任务等业务数据按组织进行隔离，不同组织之间的数据互不可见。
通过以上设计，系统能够基本形成从数据录入、算法求解、结果展示到生产管理的完整业务流程，为柜门板材切割排版业务提供一定的信息化支持。
3.3 数据库设计
　　数据库是柜门板材切割排版系统保存业务数据、支撑算法调用和实现结果追溯的重要基础。结合系统业务流程，数据库需要对用户账号、客户资料、板材规格、订单信息、待切割板件、余料信息、排样结果、算法任务和生产任务等数据进行统一管理。本文采用MySQL8.0作为系统关系型数据库，数据库名称为board_cutting_db，存储引擎采用InnoDB，以保证事务一致性、外键约束和并发访问能力。数据库字符集采用utf8mb4，以满足中文客户信息、板材名称、备注说明及JSON数据存储需求。
　　在数据库设计过程中，本文遵循以下原则：第一，围绕系统核心业务流程进行建模，使数据表能够支撑客户管理、板材管理、订单录入、排样计算、结果保存和生产任务管理等功能；第二，合理设置主键、外键和唯一约束，保证数据之间的关联完整性；第三，对订单排样参数、算法输出结果等结构变化较大的数据采用JSON字段进行保存，提高系统扩展性；第四，对客户、板材、订单等历史业务数据保留必要快照，避免基础资料后续修改影响历史订单的查询和复核。
3.3.1 数据库需求分析
　　根据柜门板材切割排版系统的功能需求，数据库主要需要满足以下几个方面的数据存储要求。
　　（1）用户与权限数据存储。系统用户需要在登录后，才能进行客户维护、板材维护、订单录入和排样计算等操作，所以数据库需要保存用户账号、密码、联系方式、账号状态和登录时间等信息。为了方便后续扩展系统管理功能，数据库中还预留了角色表、权限表、用户角色关联表和角色权限关联表，用来支持不同类型用户的权限控制。
　　（2）基础业务资料存储。系统需要对客户资料和板材规格信息进行长期维护。客户资料主要包括客户名称、联系电话、地址、启用状态和备注等内容；板材规格信息主要包括品牌、材质、颜色、规格类型、长度、宽度、厚度、使用次数和启用状态等内容。这些数据是后续创建订单、选择原料板材以及调用排样算法的重要基础。
　　（3）订单与板件数据存储。一个客户可以对应多个加工订单，一个订单中也可以包含多个需要切割的柜门板件。订单表主要用于保存订单编号、客户快照、加工名称、订单状态、原料板配置、余料配置和排样参数等信息；订单明细表主要用于保存板件名称、板件编号、尺寸、数量、材质、颜色、封边信息、纹理方向和是否允许旋转等数据。
　　（4）余料与排样结果数据存储。柜门板材在切割之后，可能会产生一些还可以继续利用的余料，所以系统需要记录余料的来源订单、原始板材、尺寸、材质、颜色和使用状态等信息。排样计算完成后，系统还需要保存板材利用率、总切割面积、使用板材数量、排样坐标结果等数据，为后续历史方案查询、生产核对和结果导出提供数据依据。
　　（5）算法任务与生产任务数据存储。在复杂订单中，排样计算可能会花费较长时间，因此数据库需要保存算法任务的输入参数、任务状态、输出结果、最优利用率、容器数量和运行耗时等信息。生产任务表则用于把订单和排样结果进一步转化为生产安排，记录任务名称、负责人、预计工时、实际工时、任务状态、开始时间和完成时间等内容。
（6）权限与组织数据存储。系统需要保存角色定义、权限定义、用户角色关联和角色权限关联等数据，以支持基于角色的权限控制。组织表用于保存组织名称、组织编码和状态等信息，用户表需要增加组织编号和组织内角色字段，以支持多组织数据隔离。
（7）审计日志与柜体模板数据存储。审计日志表用于记录操作用户、操作模块、操作类型、请求参数、客户端IP、执行耗时和操作状态等信息，为系统操作追溯提供数据依据。柜体模板表用于保存柜体设计方案的JSON结构、模板名称、品类和缩略图等信息，支持模板的复用和管理。
3.3.2 数据库概念结构设计
　　数据库概念结构设计主要通过实体及实体之间的联系来描述系统数据模型。根据系统业务需求，本文提取出用户、客户、板材、订单、订单明细和排样结果等主要实体。用户实体用于表示系统登录账号，是客户、板材和订单等业务数据的数据归属基础；客户实体用于记录加工客户资料；板材实体用于记录原料板材规格；订单实体是系统数据库设计的核心；订单明细实体用于描述待切割板件；排样结果实体用于保存算法输出的板材利用率、板件坐标和文件路径等信息。

　　各实体之间的主要关系如下：一个组织可以拥有多个用户，一个用户可以拥有多个角色，一个角色可以关联多个权限；一个用户可以维护多个客户，一个用户也可以维护多种板材规格；一个客户可以产生多个加工订单；一个订单可以包含多个订单明细；一个订单可以生成一个或多个排样结果；一个订单可以生成多个生产任务；订单明细可以引用板材规格，排样结果与订单关联保存。此外，系统还包含柜体模板实体，用于保存可复用的柜体设计方案；审计日志实体用于记录系统关键操作。通过上述关系设计，系统能够将组织、用户、角色、客户、板材、订单、板件尺寸、排样结果、生产任务和柜体设计连接起来，支撑柜门板材切割排版的完整业务流程。

3.4 本节小结
　　综上所述，本文数据库设计以订单为核心，将用户、客户、板材、订单明细、排样结果、生产任务和柜体模板等实体连接起来。在原有业务表基础上，系统新增了组织表、角色表、权限表、生产任务表、柜体模板表和审计日志表等数据表，并在各业务表中增加org_id字段以支持多组织数据隔离。该设计能够满足柜门板材切割排版系统在权限控制、组织管理、基础资料维护、订单录入、排样计算、结果保存、生产任务管理和柜体设计等方面的功能需求。通过主外键约束、唯一约束和JSON字段的合理使用，系统能够在保证数据完整性的同时保持较好的扩展性。
